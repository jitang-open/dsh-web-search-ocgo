# max_uses 对 token 成本与结果质量的影响曲线（阶段 0 spike #3）

> **实测时间**：2026-10-01
> **端点**：`POST https://opencode.ai/zen/go/v1/messages`　**模型**：`deepseek-v4.1-flash`　**max_tokens**：4096
> **脚本**：`bench/maxuses-bench.mjs`　**原始数据**：`bench/maxuses-raw.json`
> **样本**：4 查询 × max_uses{1,2,3,5} × 2 次 = **32 次请求，全部 HTTP 200，零失败零限流**

## 1. 实验设计

- **固定会话 UUID**：`d5b0a1c2-7f31-4e88-9a04-6b2c1f0d3e57`（全部 32 次共用，模拟「会话头稳定化」）
- **串行执行**，每次间隔 1 s；查询复用计划文档 §3.4 的 4 条，保证可比性
- **同格连跑 2 次**：run1 / run2 用于观察 Go 侧 prompt cache 是否随会话头稳定而生效

## 3. 四条结论

### 结论 1：max_uses 从 5 降到 2，**平均 input token 并未真实下降**

| 口径 | mu=2 | mu=5 | 变化 |
|---|---|---|---|
| 平均 `input_tokens`（原始字段） | 3597 | 3129 | **−15.0%** |
| **平均总 prompt**（in + cache_read） | 8125 | 8185 | **+0.7%（不降反微升）** |

**那 −15% 是缓存噪声，不是真实节省。** 证据链：

1. **同查询内总 prompt 几乎恒定**（见 §2.2）：`leeyoung1` 查询在 8 次里恒为 **6384** token（极差 11，0.2%）；`OpenCode Go 订阅` 极差 60（1.1%）；`DeepSeek Harness 0.1.7` 极差 212（2.4%）。总载荷与 max_uses 无关。
2. **缓存桶是固定块命中/未命中**：`leeyoung1` 各次组合为 `368+6016`、`5978+384`、`6000+384` —— 和恒为 6384，只是在 `≈6016` 的缓存块上命中或未命中。命中与否是时序偶然，不由 max_uses 决定。
3. **方向在 run 内反转**：run1 冷启动时 mu=2（2876）反而**高于** mu=5（2483）；run2 时 mu=3（1632）最低。没有任何单调趋势。
4. 唯一极差较大的查询 `dsh 插件市场`（12.6%）是 Go 服务端搜索本身的结果波动（该查询总载荷在 10745–13709 间跳变），与 max_uses 无对应关系。

**结果条数完全不变**：见 §2.1，每条查询在 mu=1/2/3/5 下返回条数**逐次完全一致**（10/10、7/7、10/10、10/10），run1/run2 也一致。

### 结论 2：max_uses=1 **仍能稳定拿到 10 条结果**，质量没有明显下降

- 4 条查询在 mu=1 下分别返回 **10 / 7 / 10 / 10** 条，与 mu=5 **逐次完全相同**。
- 全局结果条数分布（32 次）按 max_uses 分层后完全对称：`mu=1..5 各为 6×10条 + 2×7条`，**零差异**。
- URL 重合度（同查询跨 max_uses 的 8 次去重集合）：`leeyoung1` 与 `dsh 插件市场` 全部 **100%**；`OpenCode Go 订阅` 91–100%；`DeepSeek Harness 0.1.7` 为 50–91%（该查询本身噪声最大，§3.4 已记录同配置重跑重合度仅 82%）。
- **根因**：32 次请求的 `usage.server_tool_use` **全部为 `{"web_search_requests":1}`** —— 每次请求模型只发起 **1 次** `web_search` 调用。`max_uses` 是**上限**而非目标值，实测中从未被触及，因此它不改变任何结果。

- **run2 的 16 次全部命中缓存**，中位 cache_read ≈ 4992–6016；最典型的一次 `DeepSeek Harness 0.1.7 / mu=3`：run1 `in=7214 cacheR=1536` → run2 `in=303 cacheR=8447`（**未缓存输入从 7214 降到 303，降 96%**）。
- 全部 32 次请求 **`cache_read` 无一为零**（min 256，median 4992，max 13312）。
- **但会话头稳定化并非缓存命中的前提**：run1（同一 UUID 首次用于该查询）也 **16/16 命中**，cache_read 已达 256–10368。说明 Go 侧 prompt cache 的作用域**宽于单个会话 UUID**（很可能按 API key/账号，且不同查询共享同一系统前缀与工具定义缓存块）。
- `cache_creation_input_tokens` **32 次全为 0**（Go 侧不回传该字段，但不影响 cache_read 可用性）。

> **对「会话头稳定化」的判定（原文档 §3.4 标注「待验证」）**：**缓存确实存在且收益巨大**（未缓存输入可降 96%），但**它不依赖会话 UUID 的稳定性** —— 随机 UUID 同样命中。因此「profile 级持久 UUID」这一优化项的**预期收益应从"提升命中率"下调为"减少路由抖动/会话亲和"**，不能拿 cache 命中当卖点。真正决定成本的是**查询级缓存**（同 query 不重复打 API），而非会话头。

### 结论 4：推荐默认值 —— **保持 5（或保守取 3），不要为了省钱降到 1/2**

理由：

1. **省钱无效**：总 prompt 载荷与 max_uses 无关（§3 结论 1），降它一分钱都省不下。
2. **风险不对称**：实测中模型只搜 1 次，是因为这 4 条查询都很"容易"。遇到需要多轮检索的复杂查询时，模型可能发起 2–3 次 `web_search`；此时 `max_uses=1` 会**硬截断**后续检索，直接损失覆盖面，且**没有任何成本收益来补偿**。
3. **保留现有行为**：当前线上配置已是 5，保持 5 意味着阶段 2 的这项改动**零行为风险**。
4. 若出于防御性考虑想收紧，**下限取 3**（覆盖绝大多数多轮检索场景）；**不建议 1 或 2**。

> 附带修正：计划文档 §6 优化清单 P1 的「`maxUses` 5 → 可配（默认 2）／预期收益：直接省 Go 额度」**应撤销**。该项无实测收益，反而有质量风险。省额度的正确抓手是 **P1 的查询缓存**（同 query 命中即 0 token，收益确定且可测）。

## 5. 异常与观察

- **零异常**：32/32 HTTP 200，**无限流（429）、无 5xx、无网络错误**，未触发重试逻辑。
- `cache_creation_input_tokens` 恒为 0：Go 端点不回传缓存写入量。**若自研插件要做成本埋点，不能依赖该字段**，只能读 `cache_read_input_tokens`。
- `input_tokens` 单字段**不可作为成本指标**（会被缓存命中率扰动出 ±100% 的假波动）。建议埋点同时记录 `input_tokens + cache_read_input_tokens` 作为「总 prompt」。
- 耗时与 max_uses 无关：6.1–7.0 s 区间波动，run 间差异大于 max_uses 间差异。
