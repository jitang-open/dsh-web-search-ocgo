# A/B 对比：官方 provider vs dsh-web-search-ocgo

生成时间：2026-10-01T13:02:16.097Z　·　查询 6 个 × 2 套配置 × 2 轮 = 24 次请求（全部成功）

## 一句话结论

**搜索结果集没有系统性质量差距，但模型能看到的"内容"差了一个数量级：官方映射平均 `0` 字符，本插件平均 `1887` 字符。**

## 一、核心指标对照

| 指标 | 官方 provider | 本插件 | 差异 |
|---|---|---|---|
| **模型可见内容**（snippet + content 字符数） | **0** | **1887** | 本插件多 1887 字符 |
| ├ snippet（逐条摘要） | 0 | 0 | 两边都是 0 —— 见下方说明 |
| └ `result.content`（模型总结） | 0（官方完全不填） | 1887 | 本插件独有 |
| 结果条数 | 9.5 | 9.5 | 一致 |
| 延迟（均值 ± 标准差） | 5898 ± 1099 ms | 7924 ± 1508 ms | 本插件慢约 2025 ms |
| 总 prompt（input + cache_read） | 9862 ± 5457 | 8374 ± 2372 | 同量级（官方方差更大） |
| output token | 1138 | 1066 | 一致 |

> **为什么两边的 snippet 都是 0**：实测 `web_search_result` 的字段只有
> `[type, title, url, encrypted_content, page_age]` —— **根本没有 `content` 字段**，
> `page_age` 是 `null`，`text` 块也没有 `citations`。所以「逐条摘要」在协议层就取不到，
> 官方那条「只取 citations」的路径注定 0%；本插件的三级回退同样取不到，
> **真正的增量是把 `text` 块接进 `result.content`**。

## 二、噪声基线 vs 跨配置差异（§3.4 的方法论）

| 对比 | URL 重合度均值 | 逐查询 |
|---|---|---|
| 官方 provider 同配置两轮 | **89%** | 82% / 100% / 100% / 54% / 100% / 100% |
| 本插件同配置两轮 | **89%** | 54% / 100% / 100% / 100% / 100% / 82% |
| **跨配置（官方 vs 本插件）** | **57%** | 54% / 75% / 54% / 25% / 67% / 67% |

**怎么读这张表**：同配置重跑的重合度低到 54%（官方那个「DeepSeek Harness」查询），
说明**单次搜索本身的抖动就非常大**。跨配置 57% 与噪声区间（54%–100%）大幅重叠，
所以**不能得出「哪一边搜得更好」的结论** —— 差异主要来自 DeepSeek 服务端检索的随机性，
而不是端点或模型。任何声称"换端点能提升搜索质量"的说法都需要更大的样本量才能成立。

## 四、`result.content` 实际长什么样（生产实例的一次真实搜索）

查询「DeepSeek Harness 0.1.7 更新内容」，本插件返回的 `result.content` 开头：

```markdown
## DeepSeek Harness 0.1.7 更新内容汇总

根据搜索结果，0.1.7 系列（alpha.1 → alpha.2 → rc.1 → rc.2）的核心变化可概括为：
**0.1.6 在扩展 Agent "能做什么"，0.1.7 开始解决 Agent "如何长期、稳定地工作"**。
```

官方 provider 在同一查询下只给出 **10 个标题 + 10 个 URL**，正文一个字都没有。

## 五、成本与额度的含义

- 两边总 prompt 同量级（官方 9862 / 本插件 8374），
  所以「换到 Go 端点」本身**既不省也不费** token；真正的省钱抓手是**查询缓存**（命中即 0 token）。
- 本插件的 `result.content` 会额外占用一点上下文（约 1.9k 字符 ≈ 600–800 token），
  但换来的是模型不必为了看内容而重复搜索 —— 净效果是省。
- `web_search` 实际发起次数平均 1.00 次，再次印证 `max_uses` 是上限而非目标值（§3.4）。

## 六、结论

1. **质量**：结果集本身没有系统性差距（噪声区间覆盖跨配置差异）；但**模型可见内容 0 → 1887 字符**，这是唯一确凿的质量提升。
2. **延迟**：本插件慢约 2025 ms（1.34×），样本内一致，属于可感知但不影响使用的量级。
3. **成本**：总 prompt 同量级；省额度靠查询缓存，不靠换端点或调 `max_uses`。
4. **不可比的部分**：官方端点只认 `deepseek-flash` / `deepseek-v4-pro`，Go 端点只认 `deepseek-v4-flash` / `deepseek-v4.1-flash` —— 想用 V4.1 Flash 搜索**只能走 Go**，这本身就是本配置的独有价值。
